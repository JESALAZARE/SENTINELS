# Sentinels site

Static site on GitHub Pages (sentinels.com.mx, repo JESALAZARE/SENTINELS, public). No server.

- `index.html` — marketing homepage (Formspree contact form).
- `client-portal/index.html` — client portal (English UI).
- `client-portal/admin.html` — admin panel (Spanish UI); publishes to GitHub via the API.
- `client-portal/profiles.js` — client types (`profile.client_type`: `supply`, `trader` = Comercializador, `guest` = Invitado). Each type sets the portal's navigation, widget categories, default dashboard, theme and texts; add later-stage trader features there. Plants, bills and contracts only exist for `supply` (gated in `energy.js`).
- `client-portal/board.js` — customizable Dashboard / My Contract widget boards. The "Market" widget `sen_demand` shows CENACE's live SEN demand / generation / forecast (the "Operación del SEN" page) through the PML Worker's `/demanda` route, refreshing every 2 minutes plus a refresh button (the Worker caches 1 minute, `&fresh=1` at most 15 s; CENACE switches between two sets of values for past hours, so the widget mirrors whatever CENACE shows).
- `client-portal/energy.js` — single source for plant/bill/contract calculations (real savings, cost per kWh, alerts, Sentinel One context). `sites.js` renders the My Sites page; `admin-sites.js` is the admin editor for plants, monthly bills (manual, CSV, PDF read by AI via the Worker's `/admin/extract`) and contracts. Data lives in the client vault as `sites[].bills[]` and `contracts[]`; bill PDFs are documents of type `bill`.
- `client-portal/sentinel-one.js` + `sentinel-one/worker.js` — "Sentinel One" AI assistant (Claude Haiku 5.5 via a Cloudflare Worker that holds the API key, checks an HMAC pass, caps spend per client/month and stores the client's encrypted chat state). Setup steps: `sentinel-one/LEEME.md`. The Worker is pasted into the Cloudflare dashboard, so it uses plain `fetch` (no build step).
- **Market data is private**: it lives in the Cloudflare R2 bucket bound to the PML Worker as `DATOS` (keys `pml/`, `fx/`, `nodos/`, `resumen/`, `demanda/`, same layout as the old `data/` folder), never in the repo or on the site. The robots sync it down from / up to R2 with the AWS CLI (`R2_*` GitHub secrets); the portal reads it only through `client-portal/market.js` (`Market.file` / `Market.get`), which sends the client's market pass (`ME.market`, HMAC(DATA_SECRET, "market:<id>") issued by the admin panel's "Datos de mercado" tab to every client); the Worker checks the pass, that the client is active and a per-client request budget. Setup: `pml-worker/LEEME.md`.
- `client-portal/prices.js` — "Market Prices" tab (CENACE PML, MDA/MTR). Data: `pml/` (60-day history of the NodosP in `index.json`), `fx/usd-mxn.json` (Banxico FIX "para pagos"; each hour converts at its own day's rate) and `nodos/catalogo.json` (latest CENACE NodoP catalog, shown by `nodos.js`), all refreshed by `.github/workflows/pml.yml` (`scripts/fetch-*.mjs`). Any catalog NodoP (`/pml`, SW-PML) or load zone / distributed node (`/pend`, SW-PEND; the "Distributed nodes" checkbox) is queried on demand through the `pml-worker/worker.js` Cloudflare Worker (setup: `pml-worker/LEEME.md`; re-paste it in Cloudflare after changing it). `xlsx.js` writes the Excel downloads. Long-term history (since 2020, every catalog NodoP and load zone): the daily robot `.github/workflows/historico-masivo.yml` (`scripts/historico-masivo.mjs`) downloads from CENACE without touching Azure, then loads a free Azure SQL database in one session (schema, SQL views and the `agg_mensual` / `agg_hora_mes` summary tables in `azure/schema.sql`; setup in `azure/LEEME.md`; credentials only in the `AZURE_SQL_*` GitHub secrets; progress in `resumen/estado.json`) and publishes one small monthly summary per NodoP / zone in `resumen/` of the bucket (closed months only, rewritten when a month closes). `client-portal/history.js` shows those summaries for a chosen month range (From / To, 1Y · 3Y · 5Y · All); its "Excel + hourly" adds the Daily and Hourly sheets (every hour of the range, fetched month by month through the PML Worker, with a NodoP / Load zone column), and both Excel buttons bring only the markets left on in the monthly chart's legend. The portal never queries Azure live.
- MDA/MTR offers (private, not public data): `.github/workflows/ofertas.yml` (`scripts/ofertas.mjs`, daily) fills the SIM forms by postback, cleans every offer report (purchase, thermal, hydro, intermittent, non-dispatchable, import, export, GI generation/consumption, hydro shadow prices) and uploads one gzip CSV per market/type/day/system to the private Cloudflare R2 bucket (`ofertas/<MDA|MTR>/<tipo>/<year>/<date>_<system>.csv.gz`, progress in `ofertas/estado.json`; credentials only in the `R2_*` secrets). Never write offers under `data/`, print them in Actions logs or upload artifacts: the repo is public. Without `--r2` the script writes the same layout to a local folder for testing. Reserve requirements (`servicios_conexos`, MDA and MTR) and MDA assigned reserves (`servicios_conexos_asignados`, Resultados MDA report 349) are stored like the offers, plus four "Real" columns that separate each reserve from CENACE's cumulative totals (Total = Sup − Reg, Rodante 10 = Rod10 − Reg, No Rodante 10 = R10 − Rod10, Sup = Sup − R10); the model uses only those. MDA results by participant (`asignacion_participantes`, 348), load assigned by zone (`carga_asignada_zona`, 350) and assigned imports / exports (`intercambios_asignados`, 347) are stored too, and the published reserve prices of the MDA and MTR (`precios_reservas`, PreEnerServConMDA 361 / PreEnerServConMTR 364; published without the 60-day lag). In the SIN the curve price is the energy crossing (no reserve withheld) plus the published 10-minute spinning reserve price (it includes the supplemental one; prices are cumulative), because CENACE passes spinning-reserve scarcity (mostly evenings, also hot afternoons) into the PML energy component; each hour keeps both parts in `formacion` and the portal shows them as "reserve scarcity". `ofertas-resumen.mjs` exports `curvaDia` and `prepararCatalogos` so model variants (env vars listed above `PARAMETROS`) can be tested on a local folder. Summaries never carry codes: companies come from the private participant catalog `catalogos/participantes.xlsx` in the offers bucket (uploaded by hand, never in the repo; CLAVE_PM prefix C supplier, U qualified user, G generator, B basic service) and plants / units get stable labels in `catalogos/plantas.json`. The same robot also stores CENACE's real demand estimate (`demanda_real/`, by balance and by withdrawals, every settlement), generation by technology (`generacion_tec/`, national, monthly per settlement) and the PML energy component for one reference NodoP per system (`pml_energia/`); then `scripts/ofertas-resumen.mjs` writes the portal summaries under `resumen/` (hourly supply curve vs PML energy component for MDA and ex-post MTR, MDA/MTR deviation, thermal costs by company and plant, hydro opportunity costs, market share (`resumen/participacion/`: qualified supply C + U by company, month, load zone and hour; generation and reserves by company; percentages only, MWh kept in `resumen/_acum/`), hourly reserve validation in `resumen/reservas/` — MDA→MTR thermal/hydro limit and reserve-offer changes vs required and assigned "Real" reserves; model fit in `resumen/ajuste/`; SIN operating-reserve series per year in `resumen/criticas/serie_<year>_SIN.json.gz` — hourly RO = available capacity (max offered thermal / hydro limits, intermittent forecast, non-dispatchable counted at `FACTOR_NODESPACHABLE` = 43 %, GI) − real generation; the factor was calibrated against the official 2025 critical hours (90 of 100 match, MAE ≈ 370 MW), and changing the formula needs a bump of `VERSION_RO` so every day is recomputed; % of demand, offered spinning / non-spinning reserve — plus the MBP critical-hours window `ventanaCriticas(year)`: the previous year's first and last official critical-hour days ±14 days, from `HORAS_CRITICAS_PUBLICADAS`, which needs each year's published dates added by hand).
- `client-portal/insights.js` — "MEM Insights" tab (trader and guest only, `profiles.js`): Overview (findings), Market share (qualified supply, generation, reserves; HHI / CR3 / CR5, load zones, hourly profile), Price formation (merit-order curve vs PML energy component, model accuracy), Dispatch (technology mix, day ahead vs real time by company), Thermal costs (company / plant), Hydro, Reserves and Critical hours (the 100 hours with the least operating reserve inside the MBP window, with each hour's Código de Red SIN state — Normal ≥ 6 %, Alert 3–6 %, Emergency < 3 % — and frequency by hour, weekday, hour × weekday, month and reserve size; a Sentinels estimate, labelled as such), read from the offers bucket's `resumen/` through the PML Worker's `/ofertas/` route (`Market.offers`, binding `OFERTAS` = `sentinels-ofertas`). The page shows companies and percentages only and never names data sources, report names or codes; keep it that way. The step chart of the supply curve is its own SVG with an hour slider (1–24, plus play): its axes fit the whole day so the curve, demand and PML lines move between hours; the rest uses `Board.charts` (pass `ranges: false` to `barChart` for frequency charts that are not time series). The Worker's `/ofertas/` route only serves the `resumen/` folders in its `OFFERS_PATH` whitelist; add new ones there and re-paste the Worker. In the day sections (Price formation, Dispatch, Reserves) the bar's operating day also has a day slider (`daySlider`: one step per day with data, ‹ › buttons, month marks) kept in sync with the date field; the section reloads 250 ms after the slider rests, and `view()` draws each load into its own box so a slower older load never overwrites the current day.
- `client-portal/crypto.js` — shared AES-GCM/PBKDF2 helpers. Everything under `client-portal/data/` is encrypted and public; never write plaintext client data there or in commit messages.

## Every page must work on phone, tablet and desktop
- Breakpoints: `1180px` (tablet landscape), `900px`/`860px` (tablet: sidebars become drawers, grids collapse), `600px` (phone).
- At ≤600px: 16px side padding, single-column grids, full-width primary buttons, inputs `font-size:16px` (prevents iOS zoom) and ≥44px tall, dialogs as bottom sheets with `max-height: calc(100dvh - 24px); overflow-y: auto`.
- No horizontal page scroll: check `document.documentElement.scrollWidth === clientWidth` at 375px; wide tables/filter rows scroll inside their own container.
- Use `100dvh` (with a `100vh` fallback) for full-height layouts.
- Verify new UI at 375×812, 768×1024 and 1366×850 before committing.

## Security conventions
- Each page keeps its `<meta http-equiv="Content-Security-Policy">`, `referrer` meta and the HTTPS/frame-guard script in `<head>`; add any new external origin to the CSP explicitly.
- Escape all user/admin-provided text before inserting HTML (`_esc` / `esc`).
- Third-party scripts need a pinned version and an SRI `integrity` hash.
